# ローカル実行・検証基盤設計

## 目的

ローカル実行・検証基盤の目的は、Archiveaを簡単に起動、確認、テスト、リセットできるようにすることです。開発者やエージェントが毎回セットアップ手順を再発見しなくて済む状態を目指します。

## 対象範囲

ローカル実行・検証基盤は次を対象にします。

- Dockerベースのローカル実行。
- バックエンドとChrome Webフロントエンドのサービス設定。
- アップロードファイル、設定値、SQLiteの永続ローカルデータ。
- ユーザー、ロール、ジャンル別閲覧権限、年齢制限を含む初期データ。
- バックエンド、Webフロントエンド、E2E確認のテストコマンド。
- 手動確認と自動検証に使うサンプルデータ。

## 想定するDockerサービス

### `backend`

- FastAPIアプリケーションを実行する。
- Composeネットワーク内でポート`8000`を公開する。
- アップロードファイルとSQLiteデータベースをマウントされたボリュームに保存する。
- ヘルスチェック用に`/health`を提供する。

### `db`

MVPではSQLiteを利用するため、独立したDBサービスは必須ではありません。最終的にMySQLへ移行する想定のため、Docker Composeには後からMySQLサービスを追加できる構成を前提にします。

### `client_web`

- ローカル開発時にVite開発サーバーを実行する。
- 環境設定からバックエンドサービスURLを利用する。
- ブラウザUIをローカルホストのポートで公開する。想定ポートは`5173`。

### 任意の`proxy`

WebアプリとAPIを同一オリジンで扱う必要が出た場合、後からリバースプロキシを追加できます。それまでは、開発用途ではViteのプロキシ設定で十分です。

## 想定するローカルコマンド

Docker対応後の標準コマンドは次を想定します。

```bash
docker compose up --build
docker compose down
```

テストコマンドは、グローバルな言語ツールチェーンに依存しなくても実行できるように、Docker Composeサービスまたはスクリプトから呼び出せる形にします。

## 設定

ローカル、Docker、将来の本番環境で異なる値は環境変数にします。

- ブラウザからAPIへ接続するための`API_BASE_URL`または`VITE_API_BASE_URL`。
- バックエンドのアップロードディレクトリパス。
- MVP用のSQLiteデータベースパス。
- 将来のMySQL接続情報。

Docker専用のホスト名をアプリケーションソースに直接埋め込まないようにします。環境ごとに変わる値は設定として扱います。

アプリケーション内の設定値はDBに保存します。環境変数は実行環境ごとの差分に限定し、ユーザーが設定画面で変更する値とは分けて扱います。

## 初期ユーザーと権限データ

ローカル実行・検証基盤では、権限確認を反復できるように初期ユーザーとジャンルを投入できるようにします。

- 管理者ユーザー: ファイル登録、メタデータ編集、ジャンル設定、閲覧制限設定を確認する。
- 一般ユーザー: 許可されたジャンルだけが一覧と検索結果に表示されることを確認する。
- 年齢制限付き一般ユーザー: 年齢制限または閲覧レベルが不足するジャンルを閲覧できないことを確認する。
- 制限付きジャンル: 年齢制限ありのドキュメントを含め、本文配信APIでも拒否されることを確認する。

初期パスワードやトークンは本番値と分け、ローカル確認専用の値として扱います。サンプルユーザーの投入手順はDocker起動時のシード処理、または文書化されたコマンドから実行できるようにします。

## DB設計方針

- MVPではSQLiteを使う。
- 最終的にはMySQLを使う。
- 設定画面で扱う設定値はDBに保存する。
- ファイル実体はファイルシステムに保存し、保存場所をDBに保存する。
- ZIPから展開した画像ページは、ページごとの保存場所、表示順、MIME typeをDBで管理する。
- ユーザー、ロール、ジャンル、年齢制限、ユーザーごとの閲覧可能ジャンルをDBで管理する。
- 管理者だけがファイル登録と権限設定を変更できるようにする。
- SQLiteからMySQLへ移行しやすいように、DB固有関数や型に依存しすぎない。

## データとフィクスチャ

ローカル実行・検証基盤は反復可能なテストデータを扱えるようにします。

- 小さなPDFフィクスチャ。
- 単一JPG/PNG/WebPフィクスチャ。
- EPUBフィクスチャ。
- 順序付き画像ページを含むZIPフィクスチャ。
- ZIPの順序を検証する場合は、ネストされたフォルダを含むZIPフィクスチャ。
- 一般ジャンル、年齢制限付きジャンル、権限外ジャンルに紐づくサンプルドキュメント。

生成されたアップロードファイル、展開済み画像、ローカルDBはGit管理から除外します。

## リセット動作

ローカルデータのリセット手順を明確に定義します。アプリケーションコードから場当たり的に削除するのではなく、Dockerボリュームを掃除する文書化されたコマンドを優先します。

## 完了条件

ローカル実行・検証基盤は、クリーンチェックアウトから次を実行できる状態で完了とします。

1. DockerでバックエンドとChromeフロントエンドを起動できる。
2. ブラウザでChromeフロントエンドを開ける。
3. サンプルPDF/JPG/PNG/WebP/EPUB/ZIPをアップロードまたは投入できる。
4. 各対応ドキュメント形式を閲覧できる。
5. 管理者ユーザーだけがファイル登録できることを確認できる。
6. 一般ユーザーが権限外ジャンルと年齢制限外ジャンルを閲覧できないことを確認できる。
7. 文書化されたコマンドから自動チェックを実行できる。
