# Archivea 概要

## 目的

Archivea は、アーカイブされたドキュメントや画像ベースの書籍を読むためのリーダーです。PDF、JPG、PNG、WebP、EPUB、画像ページを含むZIPファイルをサポートします。

## 対象の優先順

1. Chromeブラウザ向けフロントエンド。
2. Dockerベースのローカル実行環境。
3. 将来のiOS/Androidアプリ。実装にはFlutterを使う。

まずはChromeで有用に動作する状態を目指します。Flutterも重要ですが、最初の提供面ではなく、将来のモバイルアプリ向け経路として扱います。

## 想定アーキテクチャ

- バックエンド: FastAPI
- Webフロントエンド: React + TypeScript + Vite
- モバイルフロントエンド: Flutter
- DB: MVPではSQLite、最終的にはMySQL
- 実行ハーネス: Docker Compose

## フロントエンド技術バージョン

Chrome Webフロントエンドでは、React、TypeScript、Viteの最新安定版を利用します。現時点の想定バージョンは次のとおりです。

- React: `19.2.6`
- TypeScript: `6.0.3`
- Vite: `8.0.13`
- Vite Reactプラグイン: `@vitejs/plugin-react` `6.0.2`

## データ管理方針

- 設定画面で扱う設定値はDBに保存する。
- 画像ファイル、EPUB、PDF、ZIPから展開した画像ページなどの実体はファイルシステムに保存する。
- ファイルの保存場所、MIME type、拡張子、ジャンル、表示順、作成日時などのメタデータはDBに保存する。
- MVPではSQLiteを利用し、開発と検証を簡単にする。
- 最終的にはMySQLを利用する想定で、DBモデルとクエリは移行しやすい形にする。

## 主なユーザーフロー

1. ユーザーがログインする。
2. ユーザーがジャンルを選ぶ。
3. ユーザーがPDF、JPG、PNG、WebP、EPUB、画像ページを含むZIPをアップロードまたは選択する。
4. バックエンドがドキュメントを保存し、APIでメタデータを公開する。
5. Chromeフロントエンドが選択ジャンルに応じたドキュメント一覧を表示する。
6. ユーザーがドキュメントを開き、ブラウザ上で読む。
7. 必要に応じて設定画面で表示や接続に関する設定を変更する。
8. 同じAPI契約を、将来のFlutterによるiOS/Androidアプリでも再利用する。

## 画面構成

初期の画面は次を想定します。

- ログイン画面: ユーザー認証を行い、認証後にジャンル選択画面へ進む。
- ジャンル選択画面: 閲覧対象のジャンルを選択し、該当するドキュメント一覧または閲覧導線を表示する。
- 設定画面: API接続先、表示設定、閲覧設定などを変更する。
- 画像表示画面: PDF、画像、EPUB、ZIPページを閲覧する。ZIPページでは1ページ/2ページ表示の切替を扱う。

Chrome Webフロントエンドでは、この画面構成を最初のUX設計の基準にします。Flutterでは将来のモバイル向けに同じ画面概念を再利用し、必要に応じてモバイル向けの操作へ調整します。

## 対応ドキュメント形式

- PDF: ドキュメント本文エンドポイントとして配信する。
- JPG/PNG/WebP: 単一画像の本文エンドポイントとして配信する。
- EPUB: EPUB本文エンドポイントとして配信する。ビューアはChrome Webフロントエンドで対応する。
- ZIP: 順序付き画像ページへ展開し、ページ単位のエンドポイントとして配信する。

ZIPページの順序はファイル名のソート順で決定します。新しい作業では、API契約を意図的に変更しない限り、この振る舞いを維持します。
