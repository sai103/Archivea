# TypeScript / React コーディング規約

## 目的

この規約は、`client_web/` のReact + TypeScript実装を読みやすく、変更しやすく、Reactの実行モデルに対して安全に保つためのルールです。新規コードと変更コードはこの規約に従います。既存コードに差異がある場合は、変更範囲で小さく揃え、規約適用だけを目的にした大規模な書き換えは行いません。

## 優先順位

規約が衝突する場合は、次の順で判断します。

1. React公式ルール。
2. TypeScriptの型安全性と`client_web/tsconfig.json`の`strict`設定。
3. このリポジトリの既存設計とAPI契約。
4. この文書のスタイル規約。

## Reactルール

### コンポーネントとHook

- コンポーネントはJSXから利用し、通常の関数として直接呼び出さない。
- HookはReactコンポーネントまたはカスタムHookのトップレベルで呼び出す。
- Hookをループ、条件分岐、ネスト関数、イベントハンドラ、早期return後で呼び出さない。
- カスタムHook名は`use`で始め、UIロジックと副作用の境界を名前から判別できるようにする。
- コンポーネント名は`PascalCase`にする。画面、パネル、操作部品の責務が膨らんだ場合は小さなコンポーネントかHookへ分ける。

### レンダーと副作用

- レンダーはprops、state、contextから出力を決める純粋な処理にする。
- データ取得、永続化、DOM連携、タイマー、ログ送信などの副作用をレンダー中に実行しない。
- 副作用はイベントハンドラまたは必要な`useEffect`系Hookへ置く。派生値を作るだけの処理を安易にEffectへ移さない。
- 同じ入力でレンダー結果が変わる処理をコンポーネント本体に置かない。現在時刻、乱数、外部可変値が必要な場合はイベントまたは副作用の境界で扱う。

### 状態とデータ

- props、state、context、Hookの引数と返り値を直接変更しない。
- 配列とオブジェクトの更新は新しい値を作る。`push`やプロパティ代入でstate内部を破壊的に更新しない。
- APIレスポンスの整形、表示用の派生値、画面状態の遷移は責務を分ける。バックエンド責務のZIP順序やドキュメント形式判定をクライアント側へ重複実装しない。
- stateは最小限に保ち、propsや既存stateから導ける値を重複して保持しない。

### propsとイベント

- propsは利用側が読める名前にする。真偽値は`is`、`has`、`can`などの意味が明確な接頭辞を優先する。
- UIイベントの受け口は`onOpen`、`onChangeMode`のように振る舞いを表す名前にする。内部ハンドラは`handleOpen`のように区別する。
- コンポーネントが表示責務を越えてAPI呼び出し、永続化、画面遷移を抱え込み始めたら、画面層、Hook、API層への分離を検討する。

## TypeScriptルール

### 型安全性

- `strict`を前提にし、型エラーを回避するためだけの`any`、過剰な型アサーション、非nullアサーションを追加しない。
- 外部入力は信用しない。APIレスポンス、URL、フォーム入力、ファイル情報は境界で型と値を検証し、画面内部では検証済みの形を扱う。
- ユニオン型、交差型、関数型エイリアスには`type`を使う。
- 拡張や`implements`を前提にしたオブジェクト契約には`interface`を使う。どちらでもよい単純な形では周辺コードに合わせる。
- 配列型は原則として`Foo[]`で書く。複雑なジェネリクス表現で読みやすさが上がる場合だけ`Array<Foo>`を使う。
- `enum`は既存の契約や外部値との対応で必要な場合に限る。閉じた選択肢は文字列リテラルユニオンを優先する。

### `null`と`undefined`

- 値が存在しない状態は型で表す。省略可能なプロパティで足りる場合は、明示的な`null`を増やさない。
- アプリ内部では`undefined`を基本にし、`null`はAPI、DOM、ライブラリなど外部契約が要求する場合に使う。
- 読み込み中、成功、空、失敗のように状態が複数ある場合は、`null`判定の組み合わせではなく判別可能なユニオン型を検討する。

### 命名

- 変数、関数、メソッド、オブジェクトメンバは`camelCase`にする。
- コンポーネント、クラス、型、`interface`は`PascalCase`にする。
- `interface`名に`I`接頭辞を付けない。
- 定数は周辺コードに合わせる。モジュール外へ固定値として公開する場合は、意味が明確な名前を優先する。
- ファイル名は既存の`client_web/`構成に合わせる。コンポーネント専用ファイルを追加する場合はコンポーネント名と対応が分かる名前にし、大小文字だけが異なる名前を混在させない。

### 書式

- インデントはスペース2つにする。
- セミコロンを使う。
- TypeScriptとJavaScriptの文字列は、エスケープやテンプレートリテラルが必要でない限りシングルクォートを使う。
- JSON、HTML属性、既存CSSの構文規則はそれぞれの形式に従う。
- 等価比較は原則として`===`と`!==`を使う。`null`と`undefined`を同時に扱う意図がある境界コードで`value == null`を使う場合は、意図が読み取れる狭い範囲に留める。

## ファイル配置

- `main.tsx`はReactのマウントとアプリ起動に絞り、画面実装、フォーム処理、API処理を置かない。
- 画面は`src/pages/<画面名>/`で画面単位にフォルダを分ける。画面固有のコンポーネント、Hook、スタイルは対応する画面フォルダの近くに置く。
- URLルーティングは`src/router/AppRouter.tsx`へ集約し、ページ間遷移を`App.tsx`のローカルstate分岐で増やさない。
- 画面コンポーネント、再利用コンポーネント、APIアクセス、型、表示状態の変換は責務ごとに分ける。
- API契約を複数画面で使う場合は、画面ごとにレスポンス型や取得処理を重複定義しない。
- テストは振る舞いを変更したコードの近くに置き、状態変換やAPI境界ほど型と失敗経路を確認する。

## レビュー観点

- レンダー中に副作用がないか。
- Hookの呼び出し順が条件で変わらないか。
- propsやstateを破壊的に変更していないか。
- API契約やドキュメント順序の責務をWeb側へ重複させていないか。
- `any`、型アサーション、`null`判定で型設計の問題を隠していないか。
- 命名とファイル配置から責務を追えるか。

## ツールで担保する項目

次を自動確認の候補にします。LintやFormatterを追加する作業では、この規約を基準に設定します。

- React Hookルールと依存配列のLint。
- レンダー純粋性を崩す実装を検出するReact向けLint。
- TypeScriptの型チェック。
- セミコロン、引用符、インデントのFormatter統一。
